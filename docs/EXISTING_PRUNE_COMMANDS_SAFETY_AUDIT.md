# Existing Scheduled Prune Commands Safety Audit

## 1. Purpose

This document audits two pre-existing scheduled prune commands that were present before the read-only database retention audit:

- `inventory:prune-affinities --days=30`
- `vault:prune-expired`

No new retention pruning system was created. No new retention pruning command was added. The only implementation change from this audit is a read-only `--dry-run` option for each existing command.

## 2. Commands Audited

| Command | Command Class | Schedule | Arguments / Options |
| ------- | ------------- | -------- | ------------------- |
| `inventory:prune-affinities --days=30` | `App\Console\Commands\PruneStaleFrequentlyBought` | Daily in `app/Console/Kernel.php` | `--days=30`, `--dry-run` |
| `vault:prune-expired` | `App\Console\Commands\PruneExpiredVaultTokens` | Daily at `02:00` in `app/Console/Kernel.php` | `--dry-run` |

## 3. Scheduler Entries Found

`app/Console/Kernel.php` contains:

```php
$schedule->command('inventory:prune-affinities --days=30')->daily();
$schedule->command('vault:prune-expired')->dailyAt('02:00');
```

No scheduler entry was added or changed by this audit.

## 4. Tables Touched

| Command | Table | Retention Category | Mutation Type | Conditions |
| ------- | ----- | ------------------ | ------------- | ---------- |
| `inventory:prune-affinities` | `frequently_bought_products` | `PROTECTED_FOREVER` | Deletes rows in normal mode | `source = automated` and `updated_at < now() - days` |
| `vault:prune-expired` | `payment_tokens` | `PROTECTED_FOREVER` | Updates rows in normal mode | `is_active = true`, expiry month/year present, expiry before current month |

Related protected tables verified by tests:

- `products`
- `product_stocks`
- `orders`
- `order_details`
- `payment_attempts`
- `cmi_callback_logs`

## 5. Safety Classification

### `inventory:prune-affinities`

The command deletes rows from `frequently_bought_products`, which the retention audit classifies as `PROTECTED_FOREVER` because it is catalog merchandising data.

The command is constrained to `source = automated` rows older than the configured age. These rows are generated by affinity/recommendation jobs and are rebuildable from order history. The command does not touch products, product stocks, product categories, orders, order details, seller ownership, uploads, payment records, or inventory logs.

Risk classification: medium risk because it deletes rows in a protected table, but acceptable after tests because the targeted subset is automated recommendation data.

### `vault:prune-expired`

The command updates `payment_tokens`, which the retention audit classifies as `PROTECTED_FOREVER` because token records are payment-related.

The command does not delete token rows. It deactivates active tokens whose stored card expiry month/year is before the current month. It does not touch orders, combined orders, payment attempts, CMI callback logs, customer payment history, refunds, wallets, or valid active tokens.

Risk classification: medium/high risk because it touches payment token records, but acceptable after tests because it only deactivates expired unusable tokens and preserves the rows.

## 6. Risk Assessment

| Command | Main Risk | Current Control |
| ------- | --------- | --------------- |
| `inventory:prune-affinities` | Could remove active/manual merchandising if conditions broaden. | Conditions restrict to stale `source = automated` rows; tests prove manual/recent rows and business tables are preserved. |
| `vault:prune-expired` | Could deactivate valid payment tokens if expiry logic is wrong. | Conditions require active token with non-null expiry month/year before current month; tests prove active valid/no-expiry tokens remain active. |

## 7. Dry-run Status

Dry-run was added to both commands.

### `inventory:prune-affinities --dry-run`

Dry-run prints:

- table name: `frequently_bought_products`
- conditions used
- candidate row count

It deletes nothing and updates nothing.

### `vault:prune-expired --dry-run`

Dry-run prints:

- table name: `payment_tokens`
- conditions used
- candidate row count

It deletes nothing and updates nothing.

## 8. Tests Added

Added `tests/Feature/Maintenance/ExistingPruneCommandSafetyTest.php`.

Coverage:

- `inventory:prune-affinities --dry-run` deletes nothing.
- `inventory:prune-affinities` never deletes products.
- `inventory:prune-affinities` never deletes product stocks.
- `inventory:prune-affinities` never deletes orders or order details.
- `inventory:prune-affinities` only removes stale automated affinity rows and preserves manual/recent rows.
- `vault:prune-expired --dry-run` updates and deletes nothing.
- `vault:prune-expired` never deletes orders.
- `vault:prune-expired` never deletes successful payment attempts.
- `vault:prune-expired` never deletes CMI callback logs.
- `vault:prune-expired` never deactivates active valid payment tokens.
- `vault:prune-expired` only deactivates expired unusable token rows.
- Scheduler entries remain daily/daily-at and are not every-minute jobs.

## 9. Remaining Risks

- `inventory:prune-affinities` still performs hard deletes in normal scheduled mode. This is acceptable only because the condition is limited to stale automated recommendation rows. Any future expansion must go through manual review.
- `frequently_bought_products` remains a protected table overall. Manual merchandising rows must never be included in automated pruning.
- `vault:prune-expired` updates payment-related rows. It should remain limited to deactivation, never deletion, and should never touch payment attempts or CMI callback proofs.
- Neither command archives affected rows. If business wants historical reconstruction of automated recommendations or token deactivation events, add audit logging in a separate reviewed change.

## 10. Recommendation

| Command | Recommendation | Reason |
| ------- | -------------- | ------ |
| `inventory:prune-affinities --days=30` | Keep enabled with dry-run/manual review available. | It deletes only stale automated, rebuildable recommendation rows and tests prove critical catalog/order tables are untouched. |
| `vault:prune-expired` | Keep enabled with dry-run/manual review available. | It deactivates expired unusable payment tokens, does not delete rows, and tests prove payment/order proof tables and valid tokens are preserved. |

Before any future pruning expansion, run the dry-run mode, review candidate counts, and keep the database retention protected-table blacklist as the hard stop.
