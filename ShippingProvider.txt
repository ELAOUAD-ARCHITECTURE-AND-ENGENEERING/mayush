Below is a complete integration plan based only on the documentation visible in the supplied screenshots.

## 1. What the supplied docs actually document

### Authentication

The docs show a 3-part auth model for partner API calls:

* `Authorization: Bearer <token>`
* `API-Key: <api key>`
* `Client-ID: <client id>`
* plus:

  * `Content-Type: application/json`
  * `Accept: application/json`

The screenshots also state:

* the bearer token is created from the ONESSTA dashboard under API Tokens
* `Client-ID` and `Api-Key` must be obtained from the client using the ONESSTA platform
* webhook management also has its own API key and secret key for signing

### Documented production endpoints

From the screenshots, these endpoints are visible:

* `POST https://api.onessta.com/api/v1/p/parcels/add`
* `POST https://api.onessta.com/api/v1/p/parcels/get_by_code`
* `POST {{env('API_URL')}}/p/parcels/tracking` or equivalent tracking route shown in docs
* `GET https://api.onessta.com/api/v1/p/products`
* `POST https://api.onessta.com/api/v1/p/products/add`
* `POST https://api.onessta.com/api/v1/p/products/update_stock`
* `GET https://api.onessta.com/api/v1/p/cities`
* `GET https://api.onessta.com/api/v1/p/pickup_cities`

### Shipment creation fields

The parcel creation doc shows these fields:

Required:

* `code` string
* `receiver` string
* `phone` string
* `price` float
* `city` integer or city object containing id
* `address` string

Optional or shown in example:

* `sku` string, refs separated by `;`, repeated ref for quantity
* `pickup_city` object
* `note`
* `product_nature`
* `can_open`
* `replace`

### Parcel info and tracking

The docs show:

* parcel info lookup by `code`
* tracking lookup by `code`
* tracking response contains a `history` array
* each history item includes:

  * `status`
  * `name`
  * `created_at`
  * `new_date`

Example statuses visible:

* `WAITING_PICKUP`
* `PICKED_UP`
* `SENT`
* `RECEIVED`
* `DISTRIBUTION`
* final webhook example also shows `DELIVERED`

### Products and stock

Documented:

* list products
* add product
* update stock

### Cities

Documented:

* list cities
* list pickup cities

### Webhooks

Documented webhook details include:

Headers:

* `Content-Type: application/json`
* `X-Api-Key`
* `X-Webhook-Event`
* `X-Signature`

Event types:

* `parcel.status_updated`
* `parcel.status_second_updated`
* `parcel.info_updated`

Signature:

* HMAC-SHA256 over raw JSON payload
* compare with `X-Signature`

Retries:

* 3 attempts
* delays of `10s`, `30s`, `60s`
* timeout `30s`
* recommendation: respond quickly and process async

### What is not documented in the supplied screenshots

These items are not shown and should not be invented:

* no shipping quote endpoint
* no label download or label format endpoint
* no sandbox base URL
* no explicit rate-limit rule
* no pagination rules
* no formal idempotency header
* no label PDF/ZPL/PNG spec
* no documented carrier service-level matrix

That means your plugin must support these as capability flags, not as completed features.

## 2. Integration conclusion

For Mayush, ONESSTA should be integrated as a reusable shipping provider plugin with these supported capabilities now:

* authentication
* shipment creation
* parcel lookup
* tracking
* city sync
* pickup city sync
* webhook processing
* optional product and stock sync

These requested capabilities cannot be fully delivered from the supplied docs alone:

* unified quoting method
* shipment creation with label retrieval
* sandbox certification

So the plugin should expose them as:

* `quote()` => capability unavailable exception or null quote adapter
* `getLabel()` => not-supported until vendor supplies endpoint/spec
* `sandbox_mode` => config placeholder pending vendor URL/credentials

## 11. Exact implementation of requested features

## 11.1 Unified quoting method

This is not documented by ONESSTA.

### Plugin behavior

Implement a unified method in your provider contract, but return a deterministic capability failure:

```php
public function quote(array $payload): array
{
    throw new UnsupportedCapabilityException(
        'ONESSTA documentation supplied does not include a quote/rating endpoint.'
    );
}
```

### Why

This keeps the provider contract reusable across carriers without pretending ONESSTA supports quoting.

Acceptance criterion:

* quote method exists
* clearly fails with a provider-capability error
* no fake calculation is returned

---

## 11.2 Shipment creation

### Request mapping

Use the documented fields:

* code
* sku
* receiver
* phone
* price
* city
* pickup_city
* address
* note
* product_nature
* can_open
* replace

### Example service flow

1. Validate local DTO
2. Resolve local city to remote `city_id`
3. Resolve pickup city if applicable
4. Call `/p/parcels/add`
5. Persist shipment row
6. Normalize status fields
7. Dispatch `ShipmentCreated`

### Label retrieval

Not documented.

### Plugin behavior

* include `supportsLabels(): false`
* include placeholder service `LabelService`
* any call to retrieve label throws `UnsupportedCapabilityException`

Do not fabricate a label URL.

Acceptance criterion:

* shipment can be created from documented payload
* response stored
* status and situation stored
* label retrieval explicitly marked unsupported

---

## 11.3 Status tracking

### Pull-based

Use `/p/parcels/tracking` with `code`.

Persist:

* shipment current status
* tracking history rows

### Push-based

Use documented webhooks.

Webhook controller flow:

1. capture raw headers and raw body
2. verify `X-Api-Key` if configured
3. verify HMAC with `X-Signature`
4. log webhook row
5. dispatch async `ProcessWebhookJob`
6. return 200 quickly

### Event handling

Support:

* `parcel.status_updated`
* `parcel.status_second_updated`
* `parcel.info_updated`

Acceptance criterion:

* both polling and webhook processing update the same shipment record consistently
* duplicate webhook calls do not duplicate history rows

---

## 11.4 Error-handling and retry logic

### API errors visible in docs

Common visible messages:

* `Unauthenticated.`
* invalid API key secret
* invalid client ID
* required field errors
* parcel or product not found
* city not found
* code already used
* reference already exists

### Error mapper

Create a normalized error map:

* 401-like remote not found or auth ambiguities -> `RemoteApiException`
* field validation -> `ValidationException`
* signature-related -> `AuthenticationException`
* unsupported feature -> `UnsupportedCapabilityException`

### Retry rules

Retry:

* timeouts
* 502, 503, 504
* transient connection exceptions

Do not retry:

* validation failures
* duplicate code/reference
* unauthenticated
* signature errors

Webhook retries are vendor-side, already documented as 10s, 30s, 60s.

Acceptance criterion:

* retriable failures use queue retry/backoff
* non-retriable failures fail immediately with a meaningful exception

## 18. Rate-limit rule handling

No rate-limit policy is shown in the supplied docs.

So design conservatively:

* max 1 immediate retry for synchronous admin actions
* queue heavy work
* stagger polling
* never poll the same parcel more often than every 5 minutes because the webhook page itself says polling every 5 minutes is the legacy alternative

Add a local throttle:

* tracking poll per parcel: 1 request / 5 min
* cities refresh: 1 request / day
* pickup cities refresh: 1 request / day

Document clearly:
“Vendor rate limits not documented, local throttling applied.”
